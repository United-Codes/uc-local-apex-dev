By default ORDS is only reachable over plain HTTP on a high port (e.g. `http://your-server:8181/ords/`). If you want to reach your environment over a real domain with a valid TLS certificate (like for a small hosted instance) the simplest approach is to run **nginx** on the host as a reverse proxy that terminates TLS and forwards requests to the ORDS container. Certificates come free from **Let's Encrypt** and renew automatically via `certbot`.

<Aside type="caution" title="Not a hardening guide">
  This exposes your environment to the public internet. Run the installer's
  secure mode ([`./install.sh
  --secure`](/products/uc-local-apex-dev/docs/getting-started/)), which disables
  the ORDS surfaces reachable without app authentication (Database REST API,
  MongoDB API, SQL Developer Web / Database Actions, debug-to-screen) and uses
  per-workspace passwords instead of the shared `Welcome_1`. <br /> For existing
  workspaces make sure the APEX admin/workspace passwords are strong, remove
  sample content you don't want public, and keep the database port (`1521`)
  closed to the outside.
</Aside>

## What you'll set up

```
Browser ──HTTPS(443)──▶ nginx (host) ──HTTP(8181)──▶ ORDS container ──▶ APEX
         ◀─HTTP(80)──▶ redirect to HTTPS
```

- nginx listens on `80` and `443` on the host.
- Port `80` serves the ACME challenge (for issuing/renewing certs) and redirects everything else to HTTPS.
- Port `443` terminates TLS and proxies `/ords/` and `/i/` to the ORDS HTTP connector on `127.0.0.1:8181`.

## Prerequisites

- A server running your `uc-local-apex-dev` stack, with the ORDS HTTP port published on the host (`8181` by default — check with `docker ps` / `podman ps`).
- **root / sudo** access on the host.
- A **domain name** with a DNS `A` record (and `AAAA` if you use IPv6) pointing to the server's public IP. Confirm it resolves before you start:

  ```bash
  getent hosts your-domain.example.com
  ```

- Ports **80 and 443 reachable from the internet**. If a firewall is active, open them (skip if no firewall is running):

  ```bash
  # firewalld (RHEL/Rocky/Alma)
  firewall-cmd --permanent --add-service=http --add-service=https && firewall-cmd --reload
  # ufw (Debian/Ubuntu)
  ufw allow 80,443/tcp
  ```

<Aside type="note" title="This guide uses Rocky Linux 10">
  Commands below use `dnf`. On Debian/Ubuntu install with `apt install nginx
  certbot`, and the nginx config lives in `/etc/nginx/sites-available/` + a
  symlink in `sites-enabled/` instead of `/etc/nginx/conf.d/`. Everything else
  is identical.
</Aside>

## Steps

<Steps>

1. **Install nginx and certbot**

   ```bash
   dnf install -y epel-release
   dnf install -y nginx certbot
   ```

2. **Create the ACME webroot and a bootstrap config**

   nginx must be running so certbot can prove domain ownership over port 80. Start with a minimal config that only serves the challenge:

   ```bash
   mkdir -p /var/www/certbot
   ```

   Create `/etc/nginx/conf.d/apex.conf` (replace `your-domain.example.com` throughout):

   ```nginx
   server {
       listen 80;
       listen [::]:80;
       server_name your-domain.example.com;

       location /.well-known/acme-challenge/ {
           root /var/www/certbot;
       }
       location / {
           return 404;
       }
   }
   ```

   ```bash
   nginx -t && systemctl enable --now nginx
   ```

3. **Obtain the certificate**

   ```bash
   certbot certonly --webroot -w /var/www/certbot \
     -d your-domain.example.com \
     --non-interactive --agree-tos \
     -m you@example.com
   ```

   On success the cert lives at `/etc/letsencrypt/live/your-domain.example.com/`.

4. **Write the full reverse-proxy config**

   Replace the contents of `/etc/nginx/conf.d/apex.conf` with the two server blocks below (adjust the domain and, if your ORDS HTTP port isn't `8181`, the `proxy_pass` port):

   ```nginx
   # HTTP: ACME challenge + redirect everything else to HTTPS
   server {
       listen 80;
       listen [::]:80;
       server_name your-domain.example.com;

       location /.well-known/acme-challenge/ {
           root /var/www/certbot;
       }
       location / {
           return 301 https://$host$request_uri;
       }
   }

   # HTTPS: TLS termination, reverse proxy to ORDS
   server {
       listen 443 ssl;
       listen [::]:443 ssl;
       http2 on;
       server_name your-domain.example.com;

       client_max_body_size 50m;

       ssl_certificate     /etc/letsencrypt/live/your-domain.example.com/fullchain.pem;
       ssl_certificate_key /etc/letsencrypt/live/your-domain.example.com/privkey.pem;

       # Modern TLS settings
       ssl_protocols TLSv1.2 TLSv1.3;
       ssl_prefer_server_ciphers off;
       ssl_session_timeout 1d;
       ssl_session_cache shared:SSL:10m;
       ssl_session_tickets off;

       access_log /var/log/nginx/apex_access.log;
       error_log  /var/log/nginx/apex_error.log;

       # Send the bare domain to ORDS
       location = / {
           return 301 https://$host/ords/;
       }

       # ORDS / APEX
       location /ords/ {
           proxy_pass http://127.0.0.1:8181/ords/;
           proxy_http_version 1.1;
           proxy_set_header Connection "";
           proxy_set_header Origin "";
           # ORDS builds absolute redirect URLs from the Host header and keeps the
           # http:// scheme — rewrite them back to https so browsers don't bounce
           # through plain HTTP. See "Troubleshooting" below.
           proxy_redirect ~^http://[^/]+/(.*)$ https://your-domain.example.com/$1;
           proxy_set_header Host $host;
           proxy_set_header X-Real-IP $remote_addr;
           proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
           proxy_set_header X-Forwarded-Proto $scheme;
           proxy_connect_timeout 600;
           proxy_send_timeout 600;
           proxy_read_timeout 600;
           send_timeout 600;
       }

       # APEX static images (/i/)
       location /i/ {
           proxy_pass http://127.0.0.1:8181/i/;
           proxy_set_header X-Forwarded-Host $host;
           proxy_set_header X-Real-IP $remote_addr;
           proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
           proxy_set_header X-Forwarded-Proto $scheme;
       }
   }
   ```

   ```bash
   nginx -t && systemctl reload nginx
   ```

5. **Make renewals reload nginx automatically**

   certbot renews certs on a schedule, but nginx keeps serving the old cert until it reloads. Add a deploy hook so every successful renewal reloads nginx:

   ```bash
   mkdir -p /etc/letsencrypt/renewal-hooks/deploy
   cat > /etc/letsencrypt/renewal-hooks/deploy/reload-nginx.sh <<'EOF'
   #!/bin/sh
   systemctl reload nginx
   EOF
   chmod +x /etc/letsencrypt/renewal-hooks/deploy/reload-nginx.sh
   ```

6. **Enable and verify auto-renewal**

   The certbot package ships a systemd timer. Make sure it's active and test the renewal end to end (uses the staging server, changes nothing):

   ```bash
   systemctl enable --now certbot-renew.timer
   systemctl list-timers certbot-renew.timer   # shows the next run
   certbot renew --dry-run                      # should report success
   ```

</Steps>

## Verify

```bash
# HTTP is redirected to HTTPS
curl -sI http://your-domain.example.com/ords/ | grep -i location   # -> https://.../ords/

# HTTPS reaches ORDS (302 to the landing/sign-in page)
curl -sI https://your-domain.example.com/ords/

# Static APEX assets load over HTTPS
curl -so /dev/null -w "%{http_code}\n" https://your-domain.example.com/i/apex_ui/css/Core.min.css
```

Then open `https://your-domain.example.com/ords/` in a browser — you should land on the APEX sign-in with a valid padlock.

## Troubleshooting

<Aside type="tip" title="ORDS redirects to http:// instead of https://">
  ORDS terminates TLS itself, so it builds its absolute redirect URLs (e.g.
  `/ords/_/landing`) from the incoming `Host` header while assuming the
  connector's own `http://` scheme — it ignores `X-Forwarded-Proto`. Without a
  fix the browser bounces `https → http → https` on every redirect. The
  `proxy_redirect` line in the config above rewrites those `Location` headers
  back to `https://`, removing the extra hop. Note the **regex form**
  (`~^http://...`) is required — the plain prefix form with a `$host` variable
  does not match reliably.
</Aside>

- **`nginx -t` fails on `options-ssl-nginx.conf`** — that helper file only exists if you use certbot's _nginx installer_ plugin. This guide issues certs with `certonly`, so the TLS settings are written inline instead (as shown). Don't `include` that file.
- **certbot can't reach the domain** — confirm DNS points at the server (`getent hosts your-domain.example.com`) and that ports 80/443 are open in both the OS firewall and any cloud provider security group.
- **502 Bad Gateway** — ORDS isn't reachable at the `proxy_pass` target. Check the container is up (`docker ps` / `podman ps`) and that the port matches (`curl -sI http://127.0.0.1:8181/ords/` on the host).
- **Redirect loop when testing with `curl`** — APEX appends a `?session=` id on the first hit and expects a cookie back. Use a cookie jar (`curl -c cj.txt -b cj.txt -L ...`); a normal browser handles this automatically.

<Aside type="note" title="Docker or Podman">
  This runs on the host and doesn't care which container engine you use — it
  only talks to the published ORDS port (`8181`). If your ORDS container
  publishes a different host port, update the `proxy_pass` ports accordingly.
</Aside>
